# Codex 介绍

## 1. 文档目标

这份文档用于说明 Codex 在本仓库中的定位、适合处理的任务，以及协作时建议遵守的基本方式。

Codex 可以理解为一个运行在项目工作区里的 AI 编程协作者。它能够阅读仓库文件、理解现有代码结构、执行命令、修改文档或代码，并在完成后给出清晰的变更说明。

## 2. Codex 是什么

Codex 不是单纯的聊天助手，而是面向软件项目的开发代理。它通常可以协助完成：

- 阅读和梳理项目结构
- 新建或修改文档
- 编写、调整和重构代码
- 排查接口、脚本、页面或数据库相关问题
- 运行本地测试、构建或检查命令
- 根据现有风格补齐功能实现
- 总结变更、风险和后续建议

在协作过程中，Codex 会优先尊重当前仓库已有的组织方式、命名习惯和技术栈，而不是随意引入新的结构。

## 3. 在本仓库中的适用场景

本仓库围绕 AI 短剧剧本售卖、前台展示、后台管理、下载流程和商业模式文档展开。Codex 适合参与以下工作：

- 补充产品、运营、商业模式和技术实现文档
- 调整前台页面文案、样式和交互逻辑
- 完善后台管理功能和接口说明
- 协助维护剧本数据、预览包和下载流程
- 检查数据库模型、种子数据和脚本逻辑
- 生成阶段性开发计划、测试报告和上线说明

对于需要改动代码的任务，Codex 会先阅读相关文件，再进行小范围、可追踪的修改。

## 4. 推荐协作方式

向 Codex 描述任务时，建议尽量说明目标和边界。例如：

```text
帮我新增一份后台功能说明文档，放到 docs 目录。
```

```text
帮我检查下载流程有没有明显问题，只做分析，先不要改代码。
```

```text
帮我把剧本详情页的购买按钮文案改得更清楚，并检查页面是否还能正常打开。
```

如果任务比较开放，Codex 会根据仓库现有结构做保守判断；如果存在高风险选择，才会停下来询问。

## 5. Codex 的工作原则

Codex 在本仓库中应遵守以下原则：

- 优先保持现有目录结构和代码风格一致
- 不随意删除或回滚用户已有改动
- 修改前先理解相关上下文
- 文档内容尽量清晰、可执行、方便后续维护
- 代码改动尽量聚焦当前任务，不夹带无关重构
- 完成后说明改了什么，以及是否做过验证

这些原则可以减少协作摩擦，让每一次变更都更容易被复查和继续迭代。

## 6. 适合交给 Codex 的任务类型

### 6.1 文档类任务

适合让 Codex 编写或整理：

- 项目说明
- 功能规划
- 测试报告
- 操作手册
- 接口说明
- 商业模式和运营方案

### 6.2 代码类任务

适合让 Codex 处理：

- 小功能开发
- 页面样式调整
- 表单和接口联调
- 脚本修复
- 数据模型补充
- 错误排查和测试补齐

### 6.3 分析类任务

适合让 Codex 输出：

- 仓库结构说明
- 当前功能完成度评估
- 风险点排查
- 后续开发优先级
- 上线前检查清单

## 7. 使用边界

Codex 可以协助判断和执行开发任务，但仍建议由项目负责人确认以下内容：

- 真实商业定价和合同条款
- 涉及用户隐私、支付和授权的关键规则
- 生产环境部署和数据迁移操作
- 需要外部账号权限的配置变更
- 最终上线前的业务验收

也就是说，Codex 适合作为高效的开发协作者，但关键业务决策仍应由人来确认。

## 8. 总结

在这个项目里，Codex 的价值主要体现在三点：

1. 快速理解现有仓库并补齐文档、代码和流程。
2. 把模糊需求拆成可以落地的实现步骤。
3. 在修改后给出清晰说明，方便团队继续维护。

合理使用 Codex，可以让项目从“想法、文档、代码、测试、复盘”之间的转换更顺畅，也能降低重复整理和手动排查的成本。
