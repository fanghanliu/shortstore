# 下载访问与用户身份规则

## 1. 文档目标

这份文档用于定义剧本免费下载、多人测试、展示状态、登录注册、游客身份识别和后续业务引导的规则。

它回答四个关键问题：

1. 同一套剧本是否允许多人下载？
2. 被下载过的剧本是否继续展示？
3. 什么情况下暂停下载或重新开放？
4. 如果不强制注册，如何知道是谁下载了剧本？

这份文档会作为后续登录注册、用户中心、测试数据回传、分成申请和独占授权功能的基础。

## 2. 基本判断

免费前三集验证包的核心作用是：

```text
获客 + 验证剧本潜力 + 筛选后续合作用户
```

所以它不应该被设计成“下载一次就下架”的稀缺商品。

更合理的定位是：

```text
多人可测试，后续授权再分层。
```

也就是说：

- 免费前三集允许多人下载。
- 下载过的剧本继续展示。
- 普通下载不产生独占权。
- 后续买断、按集、分成、独占授权需要单独确认。

## 3. 多人下载规则

### 3.1 默认规则

同一套剧本的免费前三集验证包，默认允许多个用户下载和测试。

规则文案：

```text
免费前三集验证包支持多人下载测试。下载不代表独占授权，也不代表获得第4集及以后内容。
```

### 3.2 为什么支持多人下载

原因：

- 不同账号的表现差异很大。
- 不同平台的推荐机制不同。
- 同一剧本在不同剪辑、封面、配音、节奏下数据会不同。
- 多人测试能帮助判断剧本真实市场潜力。

如果只允许一个人下载，平台很难收集足够样本，也很难判断剧本是否值得继续商业化。

### 3.3 多人下载的边界

多人下载只适用于：

- 前三集免费测试。
- 非独占授权。
- 未暂停开放的剧本。

不适用于：

- 完整剧本包。
- 第4集及以后内容。
- 独占买断后的剧本。
- 已归档或风险暂停的剧本。

## 4. 被下载后是否继续展示

### 4.1 默认继续展示

剧本被下载后，仍然继续展示。

原因：

- 下载次数是热度信号，不是下架条件。
- 多人测试有助于收集更多数据。
- 剧本库需要保持内容丰富度。
- 用户可能先浏览、收藏、对比，再决定下载。

### 4.2 展示和下载分开控制

剧本应该有两个层级的状态：

```text
展示状态：是否在剧本库可见
下载状态：是否允许下载免费包
```

不要只用一个 `status` 混合所有含义。

例如：

| 展示状态 | 下载状态 | 用户看到什么 |
| --- | --- | --- |
| 展示 | 可下载 | 正常卡片 + 下载入口 |
| 展示 | 暂停下载 | 正常卡片 + 暂停开放提示 |
| 展示 | 候补申请 | 正常卡片 + 申请候补入口 |
| 隐藏 | 不可下载 | 剧本库不展示 |

## 5. 剧本状态建议

当前 `Script.status` 已有：

```text
draft / published / archived
```

后续建议扩展为更明确的业务状态。

### 5.1 展示状态

建议字段：

```text
visibilityStatus
```

可选值：

| 状态 | 含义 |
| --- | --- |
| `draft` | 草稿，不公开 |
| `published` | 公开展示 |
| `hidden` | 隐藏，不在剧本库展示 |
| `archived` | 归档，不对外展示 |

### 5.2 下载状态

建议字段：

```text
downloadStatus
```

可选值：

| 状态 | 含义 |
| --- | --- |
| `open` | 可下载 |
| `paused` | 暂停下载 |
| `quota_full` | 免费测试名额已满 |
| `exclusive_locked` | 已被独占锁定 |
| `version_updating` | 文件更新中 |

### 5.3 当前 MVP 的映射

在没有新增字段前，先使用：

```text
Script.status = published
ScriptAsset.isPublic = true
ScriptAsset.status = published
```

表示：

```text
剧本展示 + 免费包可下载
```

后续进入登录注册阶段时，再补细分字段。

## 6. 暂停下载规则

以下情况可以暂停免费包下载。

### 6.1 测试名额已满

例如设置：

```text
freeDownloadQuota = 50
```

当下载人数达到 50 后：

- 剧本仍然展示。
- 下载按钮改为“名额已满”。
- 提供“申请候补”或“咨询后续”入口。

### 6.2 独占授权已成立

如果某个用户购买了独占权：

- 停止新用户下载该剧本免费包。
- 剧本可以继续展示为“已独占授权”或直接隐藏。
- 已下载用户只能继续使用前三集测试授权，不能获得后续内容。

### 6.3 文件版本更新

如果免费包内容需要修订：

- 暂停下载。
- 标记 `version_updating`。
- 新版本完成后重新开放。

### 6.4 风险暂停

如果剧本涉及平台敏感内容、版权争议或业务风险：

- 暂停下载。
- 保留后台记录。
- 前端显示“暂不开放”。

## 7. 重新开放规则

暂停后的剧本可以在以下情况下重新开放：

- 免费包更新到新版本。
- 测试数据不足，需要继续收集样本。
- 独占意向失败或过期。
- 原合作方放弃后续授权。
- 风险内容已修改完成。
- 平台决定重新开启测试名额。

重新开放时必须记录：

- 开放时间。
- 开放版本。
- 开放原因。
- 是否重置下载名额。

## 8. 游客下载如何识别

### 8.1 游客下载可识别到什么程度

如果不注册，平台不能准确知道真实身份。

但可以记录：

| 字段 | 含义 |
| --- | --- |
| `visitorId` | 浏览器本地生成的匿名访客 ID |
| `ipAddress` | IP 地址 |
| `userAgent` | 浏览器和设备信息 |
| `referrer` | 来源页面 |
| `scriptId` | 下载了哪套剧本 |
| `assetId` | 下载了哪个版本的免费包 |
| `createdAt` | 下载时间 |
| `licenseConfirmed` | 是否确认授权边界 |

这能回答：

- 哪套剧本被下载最多。
- 哪些访客重复下载。
- 哪个来源带来下载。
- 哪个版本被下载。

但不能回答：

```text
这个人到底是谁？
```

### 8.2 为什么不建议下载前强制注册

下载前强制注册会增加摩擦。

当前平台正在建立信任，免费前三集是信任入口。如果用户还没看到内容就被要求注册，容易产生：

- 不透明感。
- 营销页感。
- “是不是要收集联系方式”的警惕。
- 转化率下降。

所以第一阶段不建议把注册放在下载前。

## 9. 下载后引导注册

更合理的方式是：

```text
游客可下载，下载后引导注册。
```

下载成功后提示：

```text
前三集验证包已开始下载。
登录后可以保存下载记录、提交测试数据、申请后续剧集或分成合作。
```

提供按钮：

- 登录/注册
- 提交测试数据
- 咨询后续剧集
- 申请分成合作

其中：

- 登录/注册是引导，不是强制。
- 提交测试数据、申请分成、购买后续必须登录。

## 10. 注册后如何绑定游客下载记录

### 10.1 绑定逻辑

注册成功后，系统读取浏览器里的 `visitorId`。

然后执行：

```text
将 Download 表中 userId 为空、visitorId 相同的记录绑定到当前 userId
```

这样用户在注册前下载过的剧本，也会出现在用户中心的“我的下载”里。

### 10.2 绑定限制

为了避免误绑定，应加限制：

- 只绑定当前浏览器的 `visitorId`。
- 只绑定最近一段时间的下载记录，例如 30 天内。
- 已绑定到其他用户的下载记录不再重复绑定。
- 如果用户清理浏览器数据，则无法自动绑定历史记录。

### 10.3 绑定提示

注册后提示：

```text
已为你保存本设备最近下载过的剧本记录。
```

## 11. 什么动作必须登录

### 11.1 游客可做

游客可以：

- 浏览剧本库。
- 查看剧本详情。
- 下载前三集免费验证包。
- 查看授权说明。

### 11.2 建议登录后做

登录后体验更好：

- 收藏剧本。
- 查看我的下载记录。
- 保存测试计划。

### 11.3 必须登录后做

以下动作必须登录：

- 提交前三集测试数据。
- 申请分成合作。
- 申请独占买断。
- 购买后续剧集。
- 查看订单。
- 查看授权文件。
- 提交收益数据。

原因是这些动作涉及业务归属、审核、交易和后续责任，必须有明确用户身份。

## 12. 下载后业务闭环

下载不应该是流程终点。

下载后应进入：

```text
下载成功 -> 制作前三集 -> 发布测试 -> 回传数据 -> 选择续作方式
```

### 12.1 下载后弹窗建议

下载成功后展示：

```text
前三集验证包已开始下载

建议下一步：
1. 制作并发布前三集
2. 记录播放、完播、评论、收藏、涨粉数据
3. 回来提交测试数据
4. 根据数据选择买断、按集或分成合作
```

按钮：

- 提交测试数据
- 咨询后续剧集
- 申请分成合作
- 稍后再说

### 12.2 后续转化入口

每个下载记录都应该关联后续动作：

- 是否提交测试数据。
- 是否咨询后续剧集。
- 是否申请分成。
- 是否购买后续内容。

后续后台看板可以统计：

```text
下载量 -> 测试数据提交率 -> 咨询率 -> 购买/分成转化率
```

## 14. API 设计建议

### 14.1 游客下载

```text
POST /api/downloads
```

保持现有接口。

后续补：

- 检查 `downloadStatus`
- 检查下载名额
- 写入 `visitorId`
- 返回下载后引导信息

### 14.2 注册后绑定游客记录

```text
POST /api/account/claim-downloads
```

请求：

```json
{
  "visitorId": "visitor_xxx"
}
```

作用：

```text
将当前 visitorId 的未绑定下载记录绑定到当前用户
```

### 14.3 我的下载

```text
GET /api/account/downloads
```

返回当前用户下载记录。

### 14.4 提交测试数据

```text
POST /api/test-reports
```

必须登录。

### 14.5 续作咨询

```text
POST /api/continuation-inquiries
```

必须登录。

### 14.6 分成申请

```text
POST /api/revenue-share/applications
```

必须登录。

## 15. 页面流程建议

### 15.1 下载前

用户在详情页看到：

- 免费包信息。
- 授权边界。
- 勾选确认。
- 下载按钮。

不要求登录。

### 15.2 下载后

下载成功后弹出：

- 下一步制作建议。
- 登录保存记录。
- 提交测试数据入口。
- 续作咨询入口。
- 分成申请入口。

### 15.3 登录后

用户进入：

```text
/account
```

看到：

- 我的下载。
- 我的测试数据。
- 我的咨询。
- 我的分成申请。

## 16. 第一版实施建议

不要第一版就做完整支付和复杂后台。

建议下一阶段只做：

1. 下载成功后的下一步引导弹窗。
2. 用户表和基础注册登录。
3. 登录后绑定同设备游客下载记录。
4. 我的下载页面。
5. 测试数据提交表单。
6. 续作咨询表单。

暂不做：

- 在线支付。
- 自动分成结算。
- 独占合同生成。
- 完整后台审核系统。

## 17. 当前建议结论

最终建议规则：

```text
免费前三集允许多人下载。
下载过的剧本继续展示。
下载限制按状态和名额控制，而不是按是否被下载过控制。
游客可以下载，但只能匿名统计。
提交数据、申请分成、购买后续必须注册登录。
注册后可绑定当前设备的游客下载记录。
独占买断成立后，停止新的免费包下载或标记已独占授权。
```

下一步建议写：

```text
docs/account-and-post-download-flow-plan.md
```

专门规划：

- 登录注册怎么做。
- 下载后弹窗怎么做。
- 用户中心第一版怎么做。
- 测试数据回传表单怎么做。
- 续作咨询和分成申请怎么接入。
