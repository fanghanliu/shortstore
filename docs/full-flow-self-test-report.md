# 整体业务流程自测报告

## 1. 自测目标

本次自测有两个目标：

1. 检查当前从用户端到后台的完整流程是否存在技术问题。
2. 梳理距离真正可面向用户的完整业务流程还缺哪些关键能力。

## 2. 当前已覆盖的核心链路

当前项目已经跑通的主链路是：

```text
用户浏览剧本库
→ 进入剧本详情
→ 下载前三集验证包
→ 注册 / 登录
→ 绑定游客下载记录
→ 用户中心查看下载记录
→ 提交测试反馈
→ 申请后续合作
→ 后台查看测试反馈
→ 后台处理合作申请
→ 后台管理剧本、用户和下载记录
```

自动回归测试已经覆盖：

```text
npm.cmd run test:api
```

包括：

- 剧本列表和详情接口
- 免费验证包下载
- 注册和登录
- 游客下载记录绑定
- 用户中心下载记录
- 用户提交测试反馈
- 后台更新测试反馈状态
- 用户端读取后台更新后的测试反馈状态
- 用户提交后续合作申请
- 后台审批后续合作申请
- 用户端读取后台审批后的合作申请状态
- 后台下载记录
- 后台用户管理
- 后台剧本上下架和主推

## 3. 本次发现并已修复的技术问题

### 3.1 用户中心没有清楚展示后台处理状态

问题：

后台把合作申请改成 `approved/contacted/rejected` 后，用户中心虽然能拿到接口数据，但页面只对 `submitted` 做了中文展示，其他状态直接显示英文。

这会让用户看不懂当前申请到底处于什么阶段。

已修复：

- 测试反馈状态增加中文展示。
- 合作申请状态增加中文展示。
- 状态下方增加下一步说明。
- 用户中心增加“刷新状态”按钮。
- 用户端接口返回 `updatedAt`，后续可以继续展示处理时间。
- 自动测试补充“后台更新后，用户端接口必须读到新状态”。

涉及文件：

```text
server.js
public/site/account.html
public/site/account.js
public/site/styles.css
scripts/smoke-api.js
```

### 3.2 回归测试原来只验证后台状态，不验证用户端同步

问题：

之前测试验证了后台能更新合作申请和测试反馈，但没有验证用户端接口是否同步显示后台处理结果。

已修复：

- 测试反馈被后台标记为 `valuable` 后，测试会检查 `/api/me/test-reports` 是否同步为 `valuable`。
- 合作申请被后台标记为 `approved` 后，测试会检查 `/api/me/continuation-requests` 是否同步为 `approved`。

## 5. 当前仍存在的业务流程缺口

下面这些不是单纯技术 bug，而是完整商业流程还没有做完。

### 5.1 合作申请通过后，没有正式交付流程

当前状态：

后台可以把合作申请改为“已通过”，用户中心也能看到“合作已通过”。

缺口：

用户看见通过后，还不能继续完成：

- 查看平台给出的正式报价。
- 确认买断 / 按集 / 分成的合作条款。
- 下载后续剧集。
- 签署或确认授权文件。
- 查看交付记录。

这是目前最影响“面向真实用户”的缺口。

### 5.2 没有订单系统

当前状态：

合作申请只是意向和审批状态。

缺口：

还没有：

- 订单编号。
- 订单金额。
- 订单类型。
- 支付状态。
- 交付状态。
- 退款或取消状态。

如果后续要做买断和按集付费，订单系统必须补。

### 5.3 没有后续剧集资源交付

当前状态：

只有免费前三集验证包可以下载。

缺口：

合作通过后，用户不能在用户中心领取：

- 第 4 集以后剧本。
- 完整剧本包。
- 分镜。
- 中英双语提示词。
- 商用授权说明。

这会导致“申请通过”停在状态展示，没有真正完成交易。

### 5.4 没有合作申请的管理员备注和跟进记录

当前状态：

后台只能改状态。

缺口：

管理员不能记录：

- 为什么通过。
- 为什么拒绝。
- 已经通过什么方式联系用户。
- 下一次跟进时间。
- 给用户的说明。

如果申请量变多，只靠状态会不够用。

### 5.5 没有用户通知系统

当前状态：

用户需要进入用户中心并点击刷新或刷新页面，才能看到后台处理结果。

缺口：

还没有：

- 站内通知。
- 邮件通知。
- 短信或微信提醒。
- 未读消息。

所以当前适合内测，不适合大规模用户提交申请。

### 5.6 没有分成合作的数据回传和结算

当前状态：

用户可以申请版权分成。

缺口：

还没有：

- 分成协议。
- 收益回传。
- 平台审核收益。
- 分成比例记录。
- 结算周期。
- 结算记录。

因此“版权分成”目前只能作为意向申请，不能作为完整业务闭环。

### 5.7 没有后台操作审计

当前状态：

后台可以改用户状态、剧本状态、反馈状态和合作申请状态。

缺口：

没有记录：

- 谁改的。
- 改了什么。
- 修改前是什么。
- 修改后是什么。
- 什么时候改的。

多人运营前必须补。

## 6. 当前项目成熟度判断

当前项目已经达到：

```text
业务验证 MVP
```

也就是：

- 可以展示剧本。
- 可以让用户下载前三集。
- 可以收集用户账号和测试数据。
- 可以收集后续合作意向。
- 可以让后台做基础运营处理。

但还没有达到：

```text
可正式交易版本
```

原因是：

- 合作通过后没有订单。
- 没有付款。
- 没有后续内容交付。
- 没有正式授权确认。
- 没有通知。
- 没有运营跟进记录。

## 7. 下一步建议

我建议下一步不要做新的剧本批量生成，也不要先做视觉大改。

当前最应该补的是：

```text
合作通过后的交付闭环
```

建议拆成 Phase 6：

### Phase 6.1：合作申请处理结果面向用户

目标：

后台处理合作申请时，可以填写给用户看的处理说明。

新增字段建议：

```text
ContinuationRequest.adminNote
ContinuationRequest.userVisibleNote
ContinuationRequest.reviewedAt
```

用户中心显示：

- 当前状态
- 平台说明
- 下一步按钮

### Phase 6.2：后续交付包

目标：

合作申请通过后，用户中心可以看到可领取资源。

新增模型建议：

```text
Delivery
DeliveryAsset
```

交付类型：

- 完整买断包
- 按集交付包
- 分成合作包

### Phase 6.3：订单 MVP

目标：

买断和按集付费可以进入订单状态，而不是只停留在申请状态。

新增模型建议：

```text
Order
OrderItem
```

第一版可以先不接在线支付，用人工确认付款状态：

```text
pending_payment
paid
delivered
cancelled
```

### Phase 6.4：通知 MVP

目标：

后台处理申请后，用户中心有明确提醒。

新增模型建议：

```text
Notification
```

先做站内通知，不急着接邮件和短信。

## 8. 当前结论

本次自测结论：

- 技术主链路仍然可跑通。
- 发现的用户中心状态展示问题已修复。
- 自动测试已补上用户端状态同步验证。
- 当前最大缺口不是“能不能申请”，而是“申请通过后如何报价、付款、授权和交付”。

下一步最合理的是做 Phase 6：合作通过后的交付闭环，而不是继续横向加页面。
