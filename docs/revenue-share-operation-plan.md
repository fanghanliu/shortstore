# 版权分成合作落地运营方案

## 1. 文档目标

本文档用于把“版权分成合作”从一个销售选项，拆成可以真实执行的业务流程。

当前项目已经支持：

```text
用户下载前三集 -> 提交测试反馈 -> 申请后续合作 -> 后台审核 -> 生成订单/交付
```

但版权分成和买断、按集购买不同。买断和按集购买是用户先付款，平台再交付内容；版权分成是平台先开放后续内容，用户未来用视频收益向平台持续结算。

因此版权分成最核心的问题不是页面怎么写，而是：

1. 平台如何控制剧本交付风险。
2. 用户如何证明真实视频数据和真实收益。
3. 双方如何确认收益口径和分成比例。
4. 用户不回传数据、不结算、转卖剧本、换账号发布时如何处理。
5. 系统应该记录哪些证据，合同应该约束哪些责任。

本文档是业务和产品设计文档，不是正式法律意见。正式上线版权分成合作前，应根据主体、地区、平台、合作对象和交易方式，由专业律师审核协议文本。

参考法律底座：

- 《中华人民共和国著作权法》：使用他人作品通常需要获得许可并约定权利义务。
- 《中华人民共和国民法典》合同编：依法成立的合同对当事人具有法律约束力。

官方参考链接：

- https://www.npc.gov.cn/c2/c30834/202011/t20201119_308796.html
- https://www.npc.gov.cn/c2/c30834/202009/t20200927_307879.html

## 2. 核心判断

版权分成不应该在 MVP 阶段做成完全自助开通。

建议采用：

```text
申请制 + 人工审核 + 合同确认 + 分批交付 + 月度回传 + 人工结算
```

原因：

- 用户没有预付完整剧本费用，平台承担内容泄露风险。
- 视频收益不一定经过平台账户，系统无法天然知道真实收益。
- 分成比例、收益口径、结算周期、账号范围必须单独确认。
- 如果没有合同和证据留存，后期很难处理隐瞒收益、转授权、停更和拒绝结算。

系统应该先做“流程账本”，不要一开始承诺自动分账。

## 3. 版权分成与其他方式的区别

| 项目 | 买断 | 按集购买 | 版权分成 |
| --- | --- | --- | --- |
| 付款方式 | 先付款 | 先付款 | 后结算 |
| 交付方式 | 可一次性交付 | 按购买范围交付 | 应分批交付 |
| 平台风险 | 中 | 低 | 高 |
| 用户风险 | 高 | 中 | 低 |
| 是否需要合同 | 建议需要 | 金额高时需要 | 必须需要 |
| 是否需要数据回传 | 可选 | 可选 | 必须 |
| 是否需要持续运营管理 | 较少 | 中等 | 很高 |

版权分成不是低价购买，也不是免费领取完整剧本。它是基于后续收益的授权合作。

## 4. 推荐合作模型

### 4.1 普通分成合作

适合个人创作者、小团队、第一次合作用户。

规则：

- 用户无需预付剧本费。
- 平台按阶段开放后续剧集。
- 用户必须按周期回传视频链接、播放数据、收益截图和结算数据。
- 平台审核后按约定比例生成结算单。
- 用户若不回传、不结算或违规使用，平台暂停后续交付。

这是当前项目最适合先落地的模型。

### 4.2 保底分成合作

适合有一定数据表现、但平台仍需要降低风险的用户。

规则：

- 用户先支付一笔低额保底费用。
- 平台开放更多剧集或更长交付周期。
- 后续收益仍按比例分成。
- 保底费用可约定为不退、可抵扣或作为最低授权费。

该模式比普通分成更安全，也更适合优质剧本。

### 4.3 深度联营合作

适合 MCN、工作室、长期合作团队。

规则：

- 双方共同确认账号、项目周期、更新节奏、收益分配。
- 可以使用共同管理账号、企业主体或 MCN 后台数据。
- 可以按月或按项目结算。
- 可以签署更正式的项目合作协议。

该模式最接近商业合作，不适合早期完全自动化。

## 5. 剧本交付策略

### 5.1 不建议一次性交付全部剧本

版权分成合作下，用户没有先支付完整剧本费用。如果一次性拿到全套剧本，会产生以下风险：

- 用户拿到全套后不继续合作。
- 用户转卖或分享剧本文件。
- 用户只回传部分视频数据。
- 用户换账号发布，平台难以追踪。
- 用户改编成其他项目后绕开结算。

因此默认不应一次性交付全部剧本。

### 5.2 推荐分批交付

建议采用：

```text
第1阶段：开放第4-10集
第2阶段：数据正常后开放第11-20集
第3阶段：结算正常后开放第21-30集
第4阶段：持续合作后按批次继续开放
```

每一批交付前检查：

- 上一批视频是否按约定发布。
- 视频链接是否完整回传。
- 播放量、收益、截图是否提交。
- 是否存在违规剪辑、违规账号、转授权或停更。
- 上一周期分成是否完成结算。

### 5.3 可一次性交付的例外情况

满足以下条件之一，可以考虑一次性交付更多内容：

- 用户已完成多次合作且结算记录良好。
- 用户支付保底费用或保证金。
- 用户是明确主体的公司或 MCN。
- 双方签署更严格的合同。
- 视频发布在平台可共同监管的账号中。

## 6. 用户准入规则

版权分成申请不应只看用户是否下载过前三集，还应看测试数据和合作可信度。

建议准入条件：

- 用户已下载该剧本前三集。
- 用户已提交至少一条测试反馈。
- 用户提供公开视频链接。
- 用户填写账号主体、平台、账号主页。
- 用户说明预计更新频率。
- 用户接受数据回传和收益结算规则。
- 用户同意签署分成合作协议。

建议后台审核关注：

- 视频是否真实发布。
- 账号是否与剧本受众匹配。
- 播放、点赞、评论、完播表现是否值得继续。
- 用户是否具备持续更新能力。
- 用户联系方式是否明确。
- 是否存在重复申请、异常账号、明显低质量搬运。

## 7. 视频制作监督

平台不应试图控制用户全部制作过程，而应监督关键节点。

### 7.1 账号范围

合同和系统都应记录：

- 发布平台
- 账号名称
- 账号主页链接
- 账号主体
- 是否允许矩阵账号发布
- 是否允许第三方代运营

默认规则：

```text
未登记账号不得使用分成剧本发布后续内容。
```

### 7.2 发布范围

每条视频应回传：

- 剧本名称
- 对应剧集
- 视频标题
- 发布平台
- 视频链接
- 发布时间
- 使用账号
- 是否投流
- 是否产生收益

### 7.3 更新频率

建议约定最低更新频率：

```text
每周至少发布 X 集，或每月发布不少于 X 集。
```

如果用户连续停更，可以触发：

- 提醒
- 暂停下一批交付
- 降低交付额度
- 终止分成合作

### 7.4 内容边界

用户不得：

- 转卖剧本文件。
- 分享剧本原文、分镜、提示词包。
- 把剧本交给未登记第三方制作。
- 擅自注册版权、商标或同名账号。
- 将剧本改成其他付费项目绕开分成。
- 擅自转授权其他账号或团队使用。

## 8. 收益口径

版权分成最容易出问题的地方是“收益到底指什么”。

合同和系统必须把收益口径拆清楚。

### 8.1 可纳入分成的收益

建议纳入：

- 平台广告收益。
- 短剧播放收益。
- 付费解锁收益。
- 平台创作者激励。
- 因该剧本视频产生的内容合作收益。
- 因该剧本视频产生的账号商业化收益，若双方明确约定。

### 8.2 可排除的收益

可考虑排除：

- 用户账号其他非本剧本视频收益。
- 用户历史视频收益。
- 与本剧本无关的直播打赏。
- 与本剧本无关的带货收入。
- 用户个人品牌合作收入，除非该合作明确因本剧本产生。

### 8.3 需要特别约定的收益

以下收益容易争议，必须单独约定：

- 带货佣金。
- 直播引流收益。
- 账号涨粉后的长期收益。
- 剪辑课、素材课、社群转化收益。
- 多平台搬运后的收益。
- 付费短剧小程序收益。

建议原则：

```text
只要收益和该剧本内容直接相关，就应纳入分成或至少纳入披露范围。
```

## 9. 收益证明方式

系统无法天然知道用户真实收益，除非收益经过平台控制的账户或接入平台数据权限。

### 9.1 可信度分级

| 方式 | 可信度 | 说明 |
| --- | --- | --- |
| 平台自有账号发布 | 高 | 收益由平台掌握 |
| 共同管理账号发布 | 高 | 双方可看后台数据 |
| MCN 后台或 API 授权 | 较高 | 可定期核验 |
| 后台截图 + 视频链接 | 中 | MVP 阶段可用 |
| 用户自填收益 | 低 | 只能作为辅助 |

### 9.2 MVP 阶段建议

早期可以要求用户每月提交：

- 视频链接清单。
- 每条视频播放量。
- 每条视频收益。
- 平台创作者后台截图。
- 收益结算后台截图。
- 提现或结算记录截图。
- 用户确认声明。

平台人工审核后生成结算记录。

### 9.3 后续增强

成熟后可以考虑：

- 接入平台数据 API。
- 要求用户授权只读数据权限。
- 使用共同管理账号。
- 绑定 MCN 后台数据。
- 自动抓取公开视频播放量。
- 截图 OCR 识别收益数字。

## 10. 结算流程

### 10.1 月度结算周期

建议先采用月度结算：

```text
每月1-5日：用户提交上月数据
每月6-10日：平台审核数据
每月11-15日：确认分成金额
每月15日前：完成付款或抵扣
```

### 10.2 结算单状态

系统后续可增加结算单状态：

| 状态 | 含义 |
| --- | --- |
| `draft` | 用户已提交，等待平台审核 |
| `reviewing` | 平台审核中 |
| `confirmed` | 双方确认金额 |
| `paid` | 已完成结算 |
| `disputed` | 数据或金额存在争议 |
| `voided` | 作废 |

### 10.3 分成计算示例

```text
本月有效收益：¥10,000
平台分成比例：30%
平台应得：¥3,000
用户保留：¥7,000
```

如果存在保底、投流成本、剪辑成本、平台手续费，需要在合同中约定是否先扣除。

## 11. 违约和暂停机制

### 11.1 触发暂停的情况

建议以下情况触发暂停继续交付：

- 用户未按周期提交数据。
- 用户拒绝提供收益证明。
- 用户连续停更。
- 用户使用未登记账号发布。
- 用户转卖或泄露剧本文件。
- 用户擅自转授权。
- 用户隐瞒收益或提供虚假截图。
- 用户未按期支付平台分成。

### 11.2 暂停后的处理

系统可支持：

- 暂停下一批剧集交付。
- 标记项目异常。
- 生成待处理提醒。
- 要求用户补交数据。
- 后台记录沟通结果。
- 必要时终止合作。

### 11.3 终止后的边界

合同应约定：

- 已发布视频是否可以保留。
- 未发布内容是否必须停止使用。
- 未结算收益如何处理。
- 用户是否需要删除本地剧本文件。
- 用户是否需要停止使用相关标题、角色和设定。

## 12. 系统功能规划

版权分成不建议直接并入普通订单逻辑。后续应单独抽象为“分成项目”。

### 12.1 新增核心对象

建议后续新增：

```text
RevenueShareProject
RevenueShareBatch
RevenueShareVideo
RevenueShareStatement
RevenueShareEvidence
```

### 12.2 RevenueShareProject 字段建议

用于记录一项分成合作项目。

| 字段 | 含义 |
| --- | --- |
| `userId` | 合作用户 |
| `scriptId` | 合作剧本 |
| `continuationRequestId` | 来源申请 |

| `authorizedAccounts` | 授权账号 |
| `currentBatch` | 当前交付批次 |
| `contractFilePath` | 合同文件路径 |
| `startedAt` | 开始时间 |
| `endedAt` | 结束时间 |

### 12.3 RevenueShareBatch 字段建议

用于记录分批交付。

| 字段 | 含义 |
| --- | --- |

| 字段 | 含义 |

## 13. MVP 落地路径

### Phase 1：文档和合同规则

先完成：

- 分成合作运营规则。
- 分成协议核心条款。
- 收益口径说明。
- 数据回传模板。
- 分批交付规则。

### Phase 2：后台分成项目手动管理

当后台通过分成申请后，不只是生成 0 元订单，而是创建分成项目。

后台可填写：

- 分成比例。
- 授权平台。
- 授权账号。
- 第一批开放集数。
- 结算周期。
- 合同文件。

### Phase 3：用户回传视频和收益

用户中心新增：

- 我的分成项目。
- 提交视频链接。
- 提交收益数据。
- 上传截图证明。
- 查看结算状态。

### Phase 4：后台审核和结算

后台新增：

- 分成项目列表。
- 视频数据审核。
- 月度结算单。
- 结算状态修改。
- 异常项目提醒。

### Phase 5：自动化增强

后续再考虑：

- 平台数据 API。
- 截图 OCR。
- 自动提醒。
- 自动生成结算单。
- 合同电子签。
- 分账或支付接口。

## 14. 当前项目应立即调整的认知

当前系统中的“版权分成”不应该继续被当作一种普通订单。

建议改成：

```text
用户申请版权分成
后台审核
后台创建分成项目
签署/上传分成协议
开放第一批剧集
用户按周期回传视频和收益
后台审核
生成结算单
确认分成
再开放下一批剧集
```

也就是说，版权分成的主线不是订单，而是项目。

订单可以用于记录保底费用、保证金或已确认结算金额，但不应该承担全部分成业务。

## 15. 下一步建议

在进入代码前，建议继续写两份文档：

1. `docs/revenue-share-agreement-terms.md`

   用于整理分成协议核心条款：授权范围、收益口径、分成比例、数据提交、违约责任、终止条件。

2. `docs/revenue-share-data-report-template.md`

   用于定义用户每月应该提交哪些视频链接、播放数据、收益数据和截图证明。

这两份文档完成后，再进入数据库和后台功能设计会更稳。
